## 设计系统与取舍

- 保留微信原生四 Tab 和原生控件。首页负责风险与录入，库存负责找和管物品，用药负责每日记录，我的负责家庭和设置。
- `app.wxss` 统一背景、容器、文字、状态色、间距和尺寸。浅灰背景采用 `#F2F2F7`，内容容器白色，主操作蓝采用 `#0062CC`。风险使用红、注意用橙、正向反馈用绿，状态配文字。主要圆角为 28rpx，通用页面边距 32rpx，关键触控目标 88rpx。
- 四类业务容器分别服务统计、动作、风险和列表。日常任务利用标题和分隔线建立层次。大字模式允许多行和高度增长。共用 `state-view` 处理空态和失败，用 `batch-form` 复用批次字段。
- Apple Design 主要参考视觉层级、列表、设置、操作面板和触控指导。Ponytail 用于控制公共组件和依赖的引入。角色素材用于品牌与空态，线性图标用于动作，物品图用于识别。
- 医疗相关提示明确为当前档案与关联记录的文本匹配结果。命中已登记的禁用关联时服务端阻止保存或新打卡。档案读取失败显示核对状态。表单的迟记阈值用于任务记录状态翻转。

首页风险统计从最多 50 个批次扩大为分页读取最多 3,000 个在库批次，取多一条识别上限。负载会随家庭数据增长，读请求数量下降之外仍需量测返回行数和延迟。补货在数据缺页时显示汇总不可用，单项数量或单位无法核对时只统计已确认项目。JSON 导出读取当前家庭可见的业务表，遇到既有单表上限会阻止生成不完整文件。

历史截图报告有用药计划一次约 9 秒的观察值。本轮源码路径、开发者工具编译与本地断言可用于验证逻辑，耗时中位数、首屏可见行数及不同设备的控制台指标需在同一套数据、设备和网络下连续实测。安装包与素材体积记录见最终报告。

### 执行前

1. 确认 WorkBuddy 项目、连接库、角色和环境对应关系，由数据库负责人确认目标。已在 PGlite 与本机 PostgreSQL 17.12 隔离库验证，真实 WorkBuddy 生产库归属、备份和实际权限状态待核实。
2. 对目标库做只读清点。核对基线表、列、约束、函数、RLS、表级与列级授权和定时任务。重点核查一人多户、跨户批次和位置引用、历史负数或异常数量、跨户用药关联及既有计划未完成场次。08 之前把现有每条成员记录视为有效，已有 `left_at` 时按该列判定。若存在重复有效成员，SQL10 的唯一索引会阻止迁移，先审查数据并由数据负责人决定修复。
3. 保存数据库快照及时间点、迁移前 schema 和授权定义、客户端当前版本，以及需比对的业务表行数。备份范围包含成员、用药、物品、批次、记录与权限对象。把备份恢复到隔离环境，验证历史关联、行数和核心读写后再进入实际切换。
4. 在隔离 WorkBuddy 测试环境按 08 → 09 → 10 → 11 顺序演练，每个文件使用它自己的事务边界。确认执行器支持整个脚本的事务语义。若平台分段执行，改走支持事务的迁移通道并重新演练。
5. 前端与 SQL 一并安排切换。旧客户端的用药计划直接写和回收站直接写在权限收紧后会失败，新客户端在新 RPC 或 `left_at` 缺失时也会报错。按下方清单验证维护窗口、旧版过渡和恢复点，再决定上线时间。用药相关提示在医疗数据异常时维持核对状态。

### 旧客户端过渡

建议以服务端可验证的停写窗口作为切换方案，并用更新提示缩短旧版用户的等待。`applyUpdate()` 需要用户正在使用的客户端具备更新处理逻辑，且已经下载新版本。断网、下载失败、长时间停留在旧版等场景仍需单独处理。 [腾讯云更新 API 说明](https://indonesia.tencentcloud.com/zh/document/product/1219/57697)

先在隔离环境验证实际能关闭哪些写入、如何等待在途请求结束，以及维护期间仍可提供哪些只读功能。优先保留用药计划和历史的查看能力，并测清用药确认与漏服作业在窗口中的表现。若要给已发布旧版展示维护和升级提示，需要提前准备可连接旧库的过渡版，并测清尚未升级的终端会看到什么。

恢复写入前，用 V3 验证核心写入和权限，再用仍运行的旧版核对受影响操作的行为。暂停范围、用户提示或恢复路径无法验收时，暂缓切换。

### 总控补充验收判据（2026-11-26）

- 演练执行时逐项记录结果和可核对证据。
- 每次演练前确认由哪一层实施服务端停写（数据库角色或授权回收、PostgREST 角色切换、仍开放的只读接口），并验证在途请求 drain 完成后才切换 schema。
- 已发布旧版本身没有 `updateManager` / `applyUpdate()` 处理逻辑；仅靠新包里的更新监听无法触达旧版用户。若要显示维护或升级提示，必须先发布一个仍可连旧库的过渡版，并在真机验证断网、下载失败、长时间不升级三种场景。
- 恢复写入前设置硬判据：V3 核心写入全部成功且无重复；旧版受影响操作要么明确失败且无部分提交，要么在允许范围内成功。任一判据不满足则继续阻塞。

### 停写窗口实现层判定

| 方案 | 拦截范围与限制 | 恢复方式 | 判定 |
| --- | --- | --- | --- |
| 数据库按权限停写 | 保留家庭隔离和读取权限。覆盖表级及列级写入权限，以及可写 RPC 的执行权限，检查 `PUBLIC`、角色继承和服务账号。漏服作业独立核对 | 验证并恢复已审阅的目标版本权限。迁移成功使用 V3 权限，迁移前中止使用旧版权限 | **独立测试库首选**。需要授权管理和事务观测能力 |
| PostgREST 切换只读角色 | 仅覆盖经该入口并被切换角色的请求。需证明既有登录凭证也会切换，且家庭身份和读取范围正确。直连和定时作业需另行处理 | 恢复角色映射，用同一批凭证复验会话与权限 | 备选。先验证 WorkBuddy 是否开放该控制面 |
| 隐藏前端写入入口 | 仅影响已更新的客户端。旧包、已发出的请求和自动重试仍可能写入 | 恢复提示与入口 | 仅配合告知用户 |

数据库方案必须覆盖 SQL 08–11 自带的写权限授予。每次迁移提交时，停写限制都须继续生效，包括新建 RPC。先在测试库验证能否把临时限制与每份迁移放进同一事务，或由独立服务端入口持续拦截普通写入。任一文件提交后出现开放间隙，就中止演练。恢复时逐项核对有效权限，避免重新开放 V3 已收紧的旧写入。 [PostgreSQL 授权回收](https://www.postgresql.org/docs/17/sql-revoke.html) · [PostgREST 角色切换](https://docs.postgrest.org/en/stable/references/auth.html)

**在途请求判据**

1. 记录服务端停写实际生效时间。以旧版和 V3 使用既有会话试写，确认新请求及重试被拒绝，计划和历史仍可读取。对漏服作业和后台写入分别确认哪些暂停、哪些允许继续，并验证它们与迁移的顺序。
2. 允许已进入数据库的事务在约定超时前提交或回滚，并记录可核对的结果。检查 API 在途记录及数据库活动，含等待锁、仍持有事务的空闲连接和相关后台任务。仅看到活动查询数为零不足以放行。超时、观测权限不足或结果无法确认时中止。 [PostgreSQL 活动视图](https://www.postgresql.org/docs/17/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW)
3. 用两组请求演练边界。一组在已进入事务后触发停写，核对该事务完整提交或回滚。另一组模拟旧客户端在两个独立写请求之间遇到停写，核对计划与场次、物品与批次及记录。首步可能已提交，相关业务状态必须在迁移前核对并处理完毕。核对通过后记下最终恢复点，再开始 SQL 08。
4. 用受控测试会话验证 V3 核心写入成功且重试无重复，再确认普通会话仍受停写限制。恢复访问时复验新旧客户端，确认旧版受限操作在第一步就被拒绝或由兼容路径完整处理。任一版本出现部分写入，继续阻塞发布。

- 生产数据库已迁移。正式 AppID 重新登录与首页、库存、用药只读检查通过。发布前复核客户端实际使用的云应用。

### 校验与恢复

- 隔离环境验证创建／加入／退出／重新加入、普通成员与管理员权限、跨家庭隔离、重复请求、计划修订冲突、历史场次保留和回收站级联。应用端再验证首批入库、批次状态变更、导出、本地重新分享和错误恢复。
- 本地 SQL 验证使用合成家庭与用户。可运行 `node scripts/verify-v3-postgres.mjs <PGlite 安装目录>`。静态和页面专项脚本分别为 `verify-static.js`、`verify-v3-home-profile.js`、`verify-inventory.js`、`verify-medication.js`。实际通过数与覆盖范围以本轮验收报告为准。
- Windows 本机 PostgreSQL 回归可执行 `scripts/verify-v3-native.ps1 -PostgresBin <PostgreSQL bin 目录> -PgDriver <Node pg 包目录>`。脚本创建仅监听回环地址的合成测试库，使用两个独立连接验证重试和计划版本竞争，执行仓库漏服语句，并从停库快照恢复到另一目录核对数据和权限。云端调度器启用、次数和角色仍须在目标环境验证。
- 指定 `-PostgrestExe <PostgREST exe 路径>` 会额外启动只监听回环地址的 PostgREST，通过小程序版 SDK 验证真实 HTTP。2026-11-26 使用 PostgREST 16.6 与 PostgreSQL 17.12 通过。脚本为模拟 `wx` 提供合成登录响应，验证工作区 SDK 的请求形状、JWT 角色、RLS 和数据库函数对外返回。 [PostgREST RPC 文档](https://docs.postgrest.org/en/stable/references/api/functions.html) · [PostgREST 16.6](https://github.com/PostgREST/postgrest/releases/tag/v16.6)
- 同一事务执行失败时回滚该文件。若前序文件已提交，停止切换，核对已应用文件及客户端状态，在隔离副本验证修复后再重试。恢复旧版需同时考虑已变更的函数、授权、数据和前端兼容。
- 已有业务写入后的恢复优先前向修复。确需还原时，先保全当前库，审查切换后新增或已修改的数据，在隔离库验证恢复点与数据回放，并由数据库负责人确认后再恢复。旧 RLS 和写权限恢复属于单独的权限变更，需要对应验收。
- 当前场次沿用设备当地日历和时间生成，存为 UTC 时间戳，按当前设备的本地日期切分今日任务。跨时区旅行、夏令时边界和家庭统一时区需单独实测。
- 已有漏服任务以 5 分钟为调度周期，按计划当前阈值处理未确认场次。修改阈值可能影响较早仍待记录的场次。切换前核对实际作业所在库、执行角色、启用状态和近期运行结果，并在隔离库验证场次边界。 [定时任务巡检](cron-health-check.md)

正式发布需经过目标环境确认、备份恢复演练、迁移验证、登录后的页面回归和真机交互验收。

### 生产切换后验收

- 更新下载失败时提示稍后重新打开，继续使用当前版本。新版本下载完成后由用户确认重启，并提示先保存正在填写的内容。自动化回归通过。用户确认开发者工具模拟失败时出现提示，随后核对「我的」页和家庭仍正常显示。真实微信版本下载失败待具备更新条件后复测。
- 发布准备阶段保留历史异常行。对悬空位置先核对原始位置和归属，必要时由数据负责人确认是否改为未指定。对删除时间残留先核对物品状态和操作记录，避免把时间字段单独当作删除依据。
