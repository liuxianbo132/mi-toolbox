## 2. 判定基准（契约 v1.3 常量 + 目标代码口径）

| 项 | 基准值 | 出处 |
|---|---|---|
| 药品临期 | danger ≤7 天，warn ≤90 天 | 契约常量 |
| 其他品类临期 | danger ≤3 天，warn ≤7 天 | 契约常量 |
| 到期日换算 | **到期日 = 生产日期 + N − 1 天，生产当天计第 1 天**（v1.2 裁决 R1=B）；录入页同时允许直接填到期日 | 契约 v1.2 常量节 |
| 开封后有效期 | **开封到期日 = 开封日 + PAO − 1，开封当天计第 1 天**（v1.2 同口径）；PAO = `items.pao_days`，开封时间 = `batches.opened_at` | 契约 v1.2 + v1.1 字段 |
| 剩余天数 | `daysUntil` = 到期日与今天零点之差，负数=已过期 | `utils/date.js` |
| 分级函数 | `urgencyLevel`: <0→expired；≤danger→danger；≤warn→warn；否则 ok（**expired 已为契约常量，v1.5 补录**） | 契约 v1.5 + `utils/date.js` |
| 开封分级 | 有 `opened_at` 的批次按 **min(到期日, 开封到期日)** 参与临期分级；「标记开封」UI 入口属 M2，M1 测试以 exec_sql 构造 | 契约 v1.5 |
| 数据口径 | 批次数量编辑必须 >0（清零用「用完」）；库存列表为**物品维度**，历史批次在详情页展示 | 契约 v1.5 |
| 漏服判定 | `scheduled_at + miss_threshold_minutes` 未确认 → **pg_cron 库内翻转 status='missed'**（v1.3，UPDATE 天然幂等）；**'escalated' 本期不使用，missed 为终态**；升级呈现 = 看板红标，不发微信消息 | 契约 v1.3 |
| 漏服扫描周期（v1.7） | pg_cron **每 5 分钟**一轮；判定延迟上界 = 阈值 + 5 分钟 | 契约 v1.7 · R7 |
| 阈值范围（v1.7） | miss_threshold_minutes 前端限 **10~120（步进 5）**，默认 30；DB 无 CHECK | 契约 v1.7 · R7 |
| doses 生成（v1.7） | **整疗程一次性生成**（保存计划即时生成）；疗程上限 180 天（前端限制）；**计划变更 = 删除未发生 pending（scheduled_at > 变更时刻）按新计划重建**，taken/missed 历史保留；**阈值修改不追溯**；start_date 早于今天的时间点不生成（不补历史） | 契约 v1.7 · R7 |
| alternate_day（v1.7） | 服药日 = **start_date + 2n 天**（日历日间隔 2 天），非服药日不生成 doses | 契约 v1.7 · R7 |
| 家庭成员 | 一人一家庭（RPC 层强制）；join/create 已有任一家庭 → `already_joined`；member 可退出（`leave_household`）；owner 可移除 member（`remove_member`）；owner 退出被拒（`owner_cannot_leave`）；四 RPC 未登录统一兜底 `not_signed_in`；create_household owner nickname 不落库 | 契约 v1.2/v1.4 |
| 冲突匹配 | `links.allergen` ∩ 查看者 `allergies` **文本精确匹配** | 契约 M2 设计说明 |

## 3. M1 用例

### M1-01 家庭创建 / 邀请码加入 / 两成员互见同一份库存

- **前置条件**：A、B 两个微信号分别登录小程序；A、B 均未加入任何家庭。
- **步骤**：
  1. A 创建家庭 `[TEST]测试之家`（`create_household`）→ 记录 profile 页邀请码
  2. A 录入物品 `[TEST]A的牛奶` + 1 个 active 批次
  3. B 输入**错误**邀请码尝试加入
  4. B 输入正确邀请码加入
  5. B **再次**输入同一邀请码（同家重复加入）
  6. B 尝试**创建**新家庭（已有家庭时建家）
  7. B 打开库存列表；B 录入 `[TEST]B的抽纸`，A 刷新库存
  8. A 观察 home 页：已加入家庭后「创建/加入」入口状态
- **期望结果**：
  1. 家庭创建成功，invite_code 服务端生成（HB+6 位格式）且 A 可复制；owner 成员 nickname 不落库（DB 中为 NULL，v1.4），UI 以 session 用户名兜底显示
  2. 错误邀请码 → `not_found` 类提示，无崩溃、无无限 loading
  3. 正确邀请码 → 加入成功，与 A 同 household
  4. 同家重复 join → **`already_joined`**（提示「已在家庭中」类文案）
  5. 已有家庭时建家 → **`already_joined`**
  6. B 可见 A 录的物品，A 可见 B 录的物品——同一份库存（RLS 按 household 隔离）
  7. A 端「创建/加入」入口已隐藏
- **问题归属**：RPC 返回码错误 / 互见失败 → **后端**（`join_household`、`create_household`、RLS）；入口显隐与提示文案 → **前端**。

### M1-02 物品 + 批次录入（含「生产日期+保质期天数」换算，v2 口径 +N−1）

- **前置条件**：A 已在家庭内，录入页可用；前端 +N−1 改动已落地（2026-11-19 已核对，依赖解除）。
- **步骤**：
  1. A 录入药品 `[TEST]钙片`，批次走「生产日期+保质期天数」方式：生产日期 2026-11-10、保质期 30 天 → 检查页面回显到期日
  2. 提交 → 详情页查看批次 expiry_date 展示
  3. exec_sql 查 `batches` 该批次落库的 `expiry_date` 与 `production_date`
  4. 另录一批次**直接填到期日** 2026-12-15（v1.2：包装印「保质期至 X 日」免换算路径）→ 落库核对
- **期望结果**：
  1. 页面回显到期日 = **2026-12-09**（生产日期 + 30 − 1，生产当天计第 1 天，v1.2 裁决 R1=B）
  2. 详情页批次列表显示 2026-12-09，与录入回显一致
  3. DB 落库 `expiry_date` = `2026-12-09`，`production_date` = `2026-11-10`
  4. 直接填路径落库原样 `2026-12-15`，不参与换算
- **问题归属**：换算值错误 → **前端**（calcExpiry）；回显与落库不一致 → **后端**/数据层；直接填路径异常 → **前端**表单。

### M1-03 临期分级边界值（药品 6/7/8 天，普通品类 2/3/4 天；v2 口径重算）

- **前置条件**：A 可录入；执行日记为 D；前端 +N−1 改动已落地（2026-11-19 已核对，依赖解除）。
- **日期构造公式（v2）**：到期日 = 生产日期 + S − 1，故 **生产日期 = 到期日 − S + 1 = D + N − S + 1**（N=目标剩余天数，S=保质期天数，任选 S 使生产日期 ≤ 今天）。
- **步骤**（示例日期基于 D=2026-11-19）：按下表录入（药品 5 条、食品 5 条，均走换算路径），完成后打开 home 临期看板逐条核对 level：

| # | 品类 | 目标剩余 | 到期日 | 录入（生产日期+天数） | 期望 level | 判据 |
|---|---|---|---|---|---|---|
| 1 | medicine | 6 天 | D+6（11-25） | 11-11 + 15 | **danger** | ≤7 |
| 2 | medicine | 7 天 | D+7（11-26） | 11-12 + 15 | **danger**（边界含 7） | ≤7 |
| 3 | medicine | 8 天 | D+8（11-27） | 11-13 + 15 | **warn** | >7 且 ≤90 |
| 4 | food | 2 天 | D+2（11-21） | 11-15 + 7 | **danger** | ≤3 |
| 5 | food | 3 天 | D+3（11-22） | 11-16 + 7 | **danger**（边界含 3） | ≤3 |
| 6 | food | 4 天 | D+4（11-23） | 11-17 + 7 | **warn** | >3 且 ≤7 |
| 7 | medicine | 0 天（今天到期） | D（11-19） | 11-15 + 5 | **danger** | 0 ≤7 |
| 8 | food | −1 天（已过期） | D−1（11-18） | 11-14 + 5 | **expired** | <0（契约 v1.5 补录） |

- **期望结果**：上表 level 逐行成立；看板排序与分组按前端实现记录实况。
- **选配断言**（药品 90 天 warn 边界）：剩余 90 天（到期 2027-02-17，生产 2026-11-11 + 99）→ warn；剩余 91 天（到期 2027-02-18，生产 2026-11-11 + 100）→ ok。
- **问题归属**：level 归属错误优先**前端**（urgencyLevel 与阈值配置在前端）；若后端直接下发 level 则改判后端——执行时先确认计算位置再定责。

### M1-04 报废 / 用完的批次不再出现在看板

- **前置条件**：A 录入物品 `[TEST]状态实验` 并添加 2 个 active 批次（均构造为剩余 2 天，用 M1-03 公式，确保初始出现在临期看板）。
- **步骤**：
  1. 确认看板出现这 2 个批次
  2. 详情页对批次 b1 执行「报废」
  3. 详情页对批次 b2 执行「用完」
  4. 返回看板刷新
  5. exec_sql 核对两批次 status（`discarded` / `used`）
  6. 观察库存列表（v1.5：物品维度）与详情页批次列表
- **期望结果**：
  1. 操作后看板不再出现 b1、b2（仅 active 批次进看板）
  2. DB 中 status 分别为 discarded / used
  3. 库存列表为**物品维度**（v1.5）：物品 `[TEST]状态实验` 仍在列表（不因批次全部终态而消失），批次历史进详情页查看
- **问题归属**：看板仍显示 → **前端**（查询过滤在前端）；status 落库错误 → **后端**/数据层写入。

### M1-05 新录物品 visibility 默认 'household'

- **前置条件**：A 可录入；新环境（r53cb）已重跑 `sql/01-rpc-household.sql`（visibility 列落库）。
- **步骤**：
  1. A 录入物品 `[TEST]visibility探针`（不主动传 visibility）
  2. exec_sql 查 `items` 该行 visibility 字段值
  3. B 端库存列表确认可见该物品（household 语义行为佐证）
- **期望结果**：
  1. DB 落库 visibility = `'household'`（列 default 生效；前端不传值时不得写入 null/空串覆盖默认）
  2. B 可见该物品
- **问题归属**：default 缺失/为 null → **后端**（建列与默认值职责）；前端显式传非默认值覆盖 → **前端**。

### M1-06 成员关系变更（v2 新增：member 退出 / owner 移除 / owner 退出被拒）

- **前置条件**：延续 M1-01 家庭（A=owner、B=member）；账号 C 可用（初始无家庭）；前端「我的」页成员管理已实现（v1.2 裁决动作 5）。
- **步骤**：
  1. C 用邀请码加入 A 的家庭 → 家庭 3 成员（A/B/C）
  2. C 在「我的」页执行「退出家庭」
  3. C 重开小程序回到「创建/加入」流，尝试查看原家庭库存
  4. C 再次用邀请码加入 A 的家庭（恢复 3 成员，为 M2 保留环境）
  5. A（owner）在成员管理页移除 C
  6. C 查看原家庭库存；A 查看成员列表
  7. A（owner）寻找「退出家庭」入口
  8. 错误分支（按可用通道）：A 对不存在的 member_id 调移除；B（member）尝试移除他人
- **期望结果**：
  1. C 加入成功，成员列表显示 C
  2. member 退出成功（`leave_household` → ok）
  3. C 回到无家庭态；**RLS 失效生效——C 看不到原家庭任何数据**；物品属于家庭不带走
  4. C 可重新加入（一人一家庭限制随退出解除）
  5. owner 移除 member 成功（`remove_member` → ok）
  6. C 再次不可见原家庭数据；成员列表仅剩 A/B
  7. owner 无退出入口（UI 隐藏）；若有 RPC 直调通道，`leave_household` 返回 **`owner_cannot_leave`**
  8. `remove_member` 对不存在目标 → `not_found`；member 调用 → `forbidden`（UI 无入口为第一层断言）；未登录兜底 `not_signed_in`（v1.4，仅可构造时验）
- **问题归属**：退出/移除后可见性未失效、RPC 返回码错 → **后端**（RPC+RLS）；入口未按角色显隐、退出流程异常 → **前端**。

### M1-07 开封后有效期与开封分级（v2.2 按 v1.5 定稿：min(到期日, 开封到期日)）

- **步骤**：
  1. 录入 `[TEST]眼药水`（category=medicine），`pao_days` = 7；批次生产 2026-11-01 + 90 天 → 到期 2026-12-29
  2. 录入后打开看板，记录该批次**开封前基准 level**
  3. 测试窗口经 exec_sql 将该批次 `opened_at` 置为当前时刻（构造开封，开封日 = D）
  4. A 重进看板/详情页观察 level 与开封到期日展示
- **期望结果**：
  1. 换算断言：开封到期日 = D + 7 − 1 = D+6（示例 11-25，开封当天计第 1 天）
  2. 开封前基准：到期 2026-12-29，剩 40 天 → **ok**
  3. `opened_at` 落库为构造时刻
  4. 开封后分级：按 **min(到期日, 开封到期日)** = min(12-29, 11-25) = 11-25（v1.5）→ 剩 6 天（药品）→ **danger**
  5. 详情页展示开封后到期日 11-25（若前端已实现该展示；未实现记观察项）
- **问题归属**：开封后 level 未变 danger → **前端**（看板惰性计算未取 min）；换算错 → **前端**（calcOpenedExpiry）；详情展示形态 → 观察项。

### M1-S1 join_household 错误与跨家重复分支

## 4. M2 用例（依赖：M2 四表落库 + pg_cron 任务部署；M1 验收通过后执行）

### M2-01 过敏档案维护权限（本人可改自己；管理员可代管家人）

- **前置条件**：A=owner、B=member 同一家庭；M2 表已落库；A、B 过敏档案初始为空。
- **步骤**：
  1. B 维护自己的过敏档案：添加「花生」「青霉素」→ 保存后重进查看
  2. A（管理员视角）进入 B 的过敏档案：添加「海鲜」→ 保存
  3. B 刷新自己的档案
  4. 反向越权：B 尝试修改 A 的过敏档案（若 UI 无入口，记录「前端已隐藏」，并以可用通道观察后端是否拦截，结论记入 §8）
- **期望结果**：
  1. B 可增删改自己的档案，保存后回显一致
  2. A 可代管 B 的档案
  3. B 能看到 A 代管添加的「海鲜」
  4. B 修改 A 的档案被拒（前端隐藏入口 + 后端权限拦截，任一缺失记录为风险项回总控）
- **问题归属**：越权未被拦截 → **后端**（RLS/权限规则）；入口未按角色隐藏 → **前端**。

### M2-02 录药关联禁用/慎用 → 该成员查看时冲突标红

- **前置条件**：B 过敏档案 = {花生, 青霉素, 海鲜}（M2-01 产物）；A 档案不含「花生」。录入药品并建关联：
  - X1 `[TEST]花生味钙片`：关联 allergen=**花生**，kind=**forbidden**
  - X2 `[TEST]海鲜钙片`：关联 allergen=**海鲜**，kind=**caution**（B 档案含海鲜——验 caution 态；「无命中」态通过删除档案后复验）
  - X3 `[TEST]花生酱合剂`：关联 allergen=**花生酱**，kind=forbidden（B 档案是「花生」，精确匹配不应命中）
- **步骤**：
  1. B 打开 X1 详情 → 观察冲突标识
  2. B 打开 X2 详情 → 观察 caution 态与 forbidden 态的视觉区分
  3. B 打开 X3 详情 → 应无冲突（精确匹配：花生 ≠ 花生酱）
  4. A（无花生过敏）打开 X1 → 应无冲突（冲突按**查看者本人**档案计算）
  5. 删除 B 档案中的「海鲜」→ B 再看 X2 → 冲突消失（档案变更即时反映）
- **期望结果**：
  1. X1 对 B 标红，展示禁用（forbidden）标识与文案
  2. X2 对 B 展示慎用（caution）标识，与禁用视觉可区分
  3. X3 对 B 无冲突（精确匹配边界成立）
  4. A 看 X1 无冲突
  5. 档案删除后冲突即时消失（无残留缓存）
- **问题归属**：标红/文案错误 → **前端**展示；命中集合算错 → 匹配计算所在方（前端 or 后端接口，执行时按实现定位；扯皮回总控）。

### M2-03 用药计划 → medication_doses 自动生成的正确性

- **前置条件**：药品 `[TEST]钙片` 已录；服药人=B；执行日记为 D（示例 D=2026-11-19）。
- **步骤**：
  1. 为 B 创建计划 P1：times=["08:00","20:00"]，freq=daily，start_date=D+1（11-20），end_date=11-22
  2. exec_sql 查 `medication_doses` 中 plan_id=P1 的记录
  3. 为 B 创建计划 P2：times=["09:00"]，freq=alternate_day，start_date=11-20，end_date=11-24
  4. exec_sql 查 P2 的 doses；同时在时间线/用药页观察展示
- **期望结果**：
  1. P1 保存计划后**即时一次性生成整疗程** **6 条**（3 天 × 2 时间点，v1.7 生成时机定案），scheduled_at = 11-20 08:00 / 11-20 20:00 / 11-21 08:00 / 11-21 20:00 / 11-22 08:00 / 11-22 20:00（**北京时间**，timestamptz 落库含正确时区偏移），status 全 pending，household_id/plan_id/item_id/member_id 关联正确
  2. 疗程**首尾均含**（end_date 当天也生成）
  3. P2 生成 **3 条**：11-20、11-22、11-24 的 09:00（alternate_day = start_date + 2n，v1.7 定案；非服药日 11-21/11-23 **不生成**）
  4. 前端时间线回显时间点与录入一致（08:00 显示 08:00，不得出现 UTC 错位）
- **选配断言**（v1.7 计划变更语义；UI 支持修改计划时执行，不支持则记录观察项）：
  1. 疗程中修改 P1（如 end_date 顺延）：未发生 pending 删除并按新计划重建；已发生的 taken/missed 保留不动
  2. 阈值修改不追溯已判定结果，仅影响后续判定
  3. start_date 早于今天：今天之前的时间点不生成（不补历史）
  4. 疗程录入上限 180 天（前端限制；构造 >180 天录入观察是否被拦）
- **问题归属**：doses 条数/时刻/时区错误 → **后端**（生成落库）；展示错位/排序错 → **前端**。

### M2-04 到点提醒 → 确认打卡 → 时间线状态翻转（v2：无推送，惰性路径）

- **前置条件**：避开 23:5x 时段执行；无订阅消息依赖（v1.3 推送不可行）。
- **步骤**：
  1. 创建计划 P3：times=["当前时刻+2 分钟"]（单时间点），miss_threshold_minutes 保持默认，服药人=B
  2. 到点后打开小程序（惰性计算路径）→ 观察时间线
  3. B 点「确认」打卡
  4. exec_sql 查该 dose 的 status 与 confirmed_at
  5. 观察 UI 是否仍可再次点击确认
- **期望结果**：
  1. 到点后该剂出现在 B 的时间线，初始 status=pending
  2. 打卡后 status → `taken`，confirmed_at ≈ 打卡时刻且时区正确
  3. 时间线视觉翻转（已服用态），重复打卡被防（按钮禁用或幂等，不覆盖首次 confirmed_at、不产生重复记录）
  4. 观察项：`subscribe.js` 埋点静默无副作用（模板 id 为空，v1.3 占位设计）
- **问题归属**：状态未落库/confirmed_at 错 → **后端**；打卡交互、防重复、视觉翻转 → **前端**。

### M2-05 漏服判定 → missed → 家人看板红标；阈值随动（v2 重写：pg_cron 库内翻转）

- **前置条件**：服药人=B，家人 A 同家庭（升级呈现的观察者）；**无微信消息依赖**（v1.3 升级呈现 = 看板红标）；pg_cron 漏服任务已部署且周期 **5 分钟**（v1.7 定案）；漏服探针用 **miss_threshold_minutes=10**（v1.7 阈值范围 10~120，前端限最小 10），出结果等待上界 = 10 + 5 ≈ **15 分钟**。
- **步骤**：
  1. 创建计划 P4：times=["当前+2 分钟"]，miss_threshold_minutes=**10**，服药人=B；到点后**不打卡**
  2. 等待超过 scheduled_at + 10 分钟 + cron 粒度（最长约 15 分钟出结果）
  3. exec_sql 查该 dose 的 status
  4. A 打开小程序 → 看板/用药汇总观察漏服红标；B 打开 → 时间线该剂状态
  5. 幂等验证：再等一个 pg_cron 周期（5 分钟）后复查 dose 状态
  6. **阈值随动**：创建 P5（threshold=60，times=["当前+2 分钟"]）→ 不打卡；约 5 分钟后查 status（超时 5 < 60 应仍 pending）；将 P5 阈值改为 10（UI 支持则 UI 改，不支持则删除重建同刻计划替代）→ 等一个 pg_cron 周期后查 status
  7. 记录 missed 后 status 是否发生任何变化（终态确认）
- **期望结果**：
  1. P4：超过 scheduled_at + 10 分钟未确认 → pg_cron 库内翻转 status=`missed`（最迟约 15 分钟内出现）
  2. A 端看板/汇总出现漏服红标（升级呈现）；B 端时间线显示 missed；**全程无任何微信消息依赖**
  3. 幂等成立：重复 cron 周期后 dose 保持 missed，无重复翻转
  4. P5：超时 5 分钟 < 60 → 仍 pending；阈值改 10 后下一 cron 周期 → missed（判定读取 plan **当前**阈值，随动成立；**已判定结果不追溯**）
  5. **missed 为终态**：status 不再流转（v1.3 裁决 'escalated' 本期不使用）
- **问题归属**：未翻转/翻转条件错/阈值不随动 → **后端**（pg_cron SQL 与判定逻辑）；红标未呈现 → **前端**（惰性汇总计算与展示）。
